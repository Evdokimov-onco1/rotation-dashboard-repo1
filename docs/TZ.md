# Техническое задание: Дашборд ротаций ординаторов ММКЦ «Коммунарка»

**Версия:** 1.1 · **Дата:** 17.07.2026 · **Для реализации в:** Claude Code

---

## 1. Цель и контекст

Ординаторы 1-го года (8 человек) в течение учебного года 2025/26 проходят ротации по подразделениям онкологического центра блоками по 2–6 недель. По завершении каждого блока заведующий-куратор подразделения должен подписать логбук ординатора (подписание происходит в отдельной программе — интеграция с ней не требуется). Проблемы, которые решает сайт: (1) кураторам неудобно отслеживать по общей Excel-таблице, кто и в какие недели у них ротируется и чей логбук пора подписать; (2) для подразделений ЦАОП в графике не указан конкретный куратор — есть несколько кандидатов, и назначение происходит вручную; (3) расписание меняется в течение года, и правки должны быть доступны администратору без пересборки сайта.

Целевой сценарий: заведующий открывает сайт, выбирает себя и сразу видит — «Бухурова Э.Р., недели 11–14 (17.11–12.12), ротация завершена — подписать логбук».

## 2. Роли и сценарии использования

**Куратор (заведующий)** — без авторизации, со стационарного компьютера. Открывает «Кабинет куратора», выбирает своё ФИО, видит: кто сейчас на ротации, кто завершил (подписать логбук), кто придёт следующим, и блоки «возможно ваши» (ЦАОП-ротации без назначенного куратора, где он среди кандидатов). Может открыть общую матрицу.

**Заведующий учебной частью** — вводит тот же PIN и открывает «Кабинет учебной части»: верхнеуровневую сводку задач кураторов на сегодня — кто должен подписать логбуки, кто принимает ординатора, сколько блоков ждут назначения куратора. Это контрольный экран для управления работой заведующих.

**Администратор** (Владимир / ответственный учебного отдела) — вводит PIN и получает право редактирования: назначает конкретных кураторов manual-блокам, переносит/создаёт/удаляет блоки при изменениях расписания, смотрит журнал правок.

**Гость** (ординатор, сотрудник) — просмотр матрицы и кабинетов без редактирования.

## 3. Модель данных

Сущности (таблицы SQLite):

**residents** — ординаторы: `id`, `fio`, `year` (год обучения, сейчас 1), `active`.

**weeks** — календарь учебных недель: `num` (1–35), `date_start`, `date_end`, `note`. Нумерация недель — сквозная по колонкам исходного графика и совпадает с тем, как ею пользуются коллеги («недели 11–14»). Неделя №17 — двухнедельный блок (11.02–20.02), это нормально и хранится как одна запись.

**units** — подразделения: `id`, `name_short` (как в графике ротации), `name_official` (официальное название отделения), `territory` (А22 / С8 / К57 / несколько), `curator_rule` (`auto` — куратор один и назначается автоматически; `manual` — кандидатов несколько, выбор вручную в админке), `color` (цвет для матрицы).

**curators** — заведующие: `id`, `fio`, `profile` (специализация/примечание), `telegram_chat_id` (nullable, для этапа 2), `email` (nullable).

**unit_curators** — связь «подразделение → кандидаты в кураторы» (у auto-подразделений ровно один, у manual — несколько).

**rotation_blocks** — блоки ротации: `id`, `resident_id`, `unit_id`, `week_from`, `week_to`, `assigned_curator_id` (nullable), `comment`. Для manual-подразделений до назначения куратора поле пусто → блок в статусе ⚠️ «куратор не назначен» и отображается всем кандидатам как «возможно ваш». Для auto-подразделений куратор проставляется автоматически при создании блока.

**audit_log** — журнал правок: `id`, `timestamp`, `action`, `block_id`, `old_value`, `new_value`. Пишется при любом изменении блоков и назначений кураторов (авторизация общая по PIN, поэтому фиксируем «что и когда», без персонализации).

**settings** — ключ-значение: хэш PIN-кода, токен Telegram-бота (этап 2) и пр.

Правила целостности:
- Блоки одного ординатора не могут пересекаться по неделям — валидация при создании/редактировании с понятным сообщением об ошибке.
- `week_from ≤ week_to`, обе в диапазоне существующих недель.
- Удаление подразделения/куратора, на которые ссылаются блоки, запрещено.

## 4. Исходные данные (сид)

При первом запуске база наполняется из сид-файла `seed.json`, который прилагается к настоящему ТЗ и содержит данные Приложений А–В в машиночитаемом виде. Источник — файлы «график_ротации_ординаторов_1_года_2025-2026.xlsx» и «Заведующие по отделениям.xlsx» с внесёнными исправлениями:

1. **Шидаева М.М., недели 13–16:** в исходном xlsx ошибочно указано ОО №4 (дублирует её же блок недель 21–24) — в сиде заменено на **ОО №2**. Подтверждено заказчиком.
2. **Неделя №24:** в исходнике «04.04–10.04», но 04.04.2026 — суббота; в сиде принято **06.04–10.04**.
3. Опечатки исходника («отдление», «химиотервпия») в названиях подразделений исправлены.

Вопросы к данным, не блокирующие разработку (правятся в админке после запуска): в графике отсутствуют недели 10.11–14.11.2025 и 13.04–17.04.2026 — предположительно учебные недели вне ротаций; неделя №35 (29.06–04.07) пуста у пяти ординаторов из восьми — отображается как «нет ротации».

## 5. Функциональные требования: интерфейс

Дизайн и поведение **утверждены заказчиком по кликабельному прототипу** — файл `docs/prototype-demo.html` в репозитории, исходники — `frontend-prototype/`. Прототип является эталоном: боевой фронтенд развивает его код, а не пишется заново. Язык интерфейса — русский; ориентация на десктоп (стационарные компьютеры заведующих), но вёрстка не должна ломаться на планшете. Отличие боевой версии от прототипа: вместо «демо-даты» используется реальная текущая дата (по московскому времени), все правки сохраняются на сервере.

### 5.1. Кабинет куратора
Выпадающий список «Я — заведующий» (ФИО + примечание о подразделении). Четыре блока сверху вниз:
- **«Сейчас у вас на ротации»** — блоки, в которые попадает текущая дата; у каждого бейдж «до {дата окончания}».
- **«Завершили ротацию — подписать логбук»** — завершившиеся блоки, свежие сверху. Формат строки: ФИО ординатора, подразделение, «недели N–M (дата – дата)».
- **«Придут следующими»** — ближайшие будущие блоки (до 4), бейдж «с {дата начала}».
- **«Возможно, ваши»** (жёлтая карточка, показывается только при наличии) — manual-блоки без назначенного куратора, где выбранный заведующий среди кандидатов, с пометкой ⚠️ «куратор не назначен».

### 5.2. Общая матрица (Гант)
Таблица: строки — 8 ординаторов (ФИО закреплено слева), столбцы — 35 недель. Блоки — цветные ячейки на всю длину блока с аббревиатурой подразделения. Обозначения: тёмная рамка — текущая неделя (и подсветка её номера в шапке), приглушённая прозрачность — завершившиеся блоки, пунктирная рамка + ⚠️ — куратор не назначен. Наведение — всплывающая подсказка (подразделение, недели, даты, куратор). Клик — карточка блока: в режиме просмотра — детали, в режиме администратора — редактор. Под матрицей — легенда цветов и пояснение обозначений.

### 5.3. Кабинет учебной части
Вкладка «Учебная часть», до авторизации — поле PIN (тот же PIN, что у админки: единая привилегированная сессия — вход в одном месте открывает оба раздела). После авторизации:
- **Сводка (три счётчика):** «логбуков ожидают подписи» · «ротаций стартует на этой неделе» · «блоков без куратора» (последний подсвечивается жёлтым при значении > 0).
- **Карточки по кураторам** — только кураторы, у которых есть задачи на сегодня; сначала те, у кого есть неподписанные логбуки. Внутри карточки:
  - бейдж **«подписать логбук»**: {ординатор} — {подразделение}, недели N–M, ротация завершилась {дата}. Показывается в течение **5 рабочих дней** после окончания блока — то же окно, что у Telegram-напоминаний (общий параметр в настройках; статус «подписано» в системе не ведётся, см. раздел 6);
  - бейдж **«принимает»**: {ординатор} — {подразделение}, недели N–M (по {дата}). Показывается, если текущая дата попадает в первую неделю блока;
  - мелким текстом — «сейчас на ротации: k чел.».
- **«Ваша задача: назначить кураторов»** — жёлтая карточка со всеми manual-блоками без куратора, отсортированными по дате старта (бейдж «старт {дата}»); само назначение выполняется во вкладке «Админка».
- Пустое состояние: «На сегодня задач у кураторов нет».

### 5.4. Админ-режим
Вкладка «Админка»: до авторизации — поле ввода PIN. После авторизации:
- **«Требуют назначения куратора»** — список всех manual-блоков без куратора (счётчик в заголовке); у каждого — выпадающий список кандидатов **только этого подразделения**; выбор сохраняется сразу.
- **Редактор блока** (клик по блоку в матрице или кнопка «+ Добавить блок»): ординатор, подразделение, неделя «с» и «по» (список с датами), куратор — для auto-подразделений проставляется автоматически и не редактируется, для manual — выбор из кандидатов или «не назначен». Кнопки: Сохранить / Отмена / Удалить.
- **Валидация при сохранении:** «с» ≤ «по»; блок не пересекается с другими блоками того же ординатора — при нарушении понятное сообщение, сохранение отклоняется.
- Ссылка на **журнал правок** (список: дата-время, действие, что изменилось).

## 6. Уведомления (Telegram) — этап 2

**Канал:** Telegram-бот (создаётся через @BotFather, токен хранится в настройках на сервере). Привязка куратора: администратор в админке генерирует для куратора одноразовый код-ссылку вида `t.me/<бот>?start=<код>`; куратор нажимает «Start» — его `chat_id` привязывается к профилю. Кураторы без привязки просто не получают сообщений (сайт для них работает как обычно).

**Расписание:** запуск скрипта рассылки **каждый рабочий день (пн–пт) в 7:00 по Москве** через Crontab панели хостинга. Праздничные дни на этапе 2 не исключаются (сообщение в праздник допустимо); при желании позже добавляется производственный календарь.

**Содержимое.** Сообщение конкретному куратору отправляется **только если есть события** (защита от спама):
1. **Начало ротации** — в первый день блока: «Сегодня к вам приходит на ротацию: {ФИО}, {подразделение}, недели N–M (по {дата})».
2. **Завершение ротации** — «Завершил(а) ротацию: {ФИО}, недели N–M — не забудьте подписать логбук». Напоминание повторяется каждый рабочий день **в течение 5 рабочих дней** после окончания блока, затем прекращается (статус «подписано» в системе не ведётся, поэтому окно напоминаний фиксированное). ⚠️ Длительность окна — параметр в настройках, значение по умолчанию согласовать с заказчиком.
3. **Понедельничный дайджест** — «Сейчас у вас на ротации: {список}».

**Администратору** по понедельникам: список manual-блоков без назначенного куратора, начинающихся в ближайшие 4 недели.

**Архитектурная заготовка этапа 1:** скрипт `notify.php` реализуется сразу, но в режиме «сухого прогона» (пишет, что отправил бы, в лог). Включение реальной отправки на этапе 2 = добавление токена бота и привязка chat_id, без изменения кода. Контакты кураторов заказчик предоставит на этапе 2.

## 7. Архитектура и технологии

**Решение заказчика:** размещение на уже оплаченном виртуальном хостинге Timeweb (PHP 8.2, панель с Crontab, SSH, файловым менеджером и SSL). Облачный сервер не используется. Монорепозиторий на GitHub:

```
/frontend           — React 18 + TypeScript + Vite + Tailwind CSS + shadcn/ui
                      (развитие утверждённого прототипа из /frontend-prototype)
/backend            — PHP 8.2 без тяжёлых фреймворков: /backend/api/*.php + общие модули
/data               — seed.json (исходные данные для первичного наполнения БД)
/docs               — ТЗ (этот документ), prototype-demo.html
/.github/workflows  — CI: сборка фронтенда и деплой на хостинг
```

**Frontend** — SPA (раздел 5), собирается в статику. На хостинге лежит в корне поддомена вместе с `api/`.

**Backend (PHP)** — REST API, те же маршруты, что были согласованы ранее, в PHP-исполнении (единая точка входа `api/index.php` с роутингом):
- `GET /api/schedule` — весь график одним ответом (недели, ординаторы, подразделения, кураторы, блоки).
- `GET /api/curators/{id}/dashboard` — данные кабинета куратора (сейчас / завершили / скоро / «возможно ваши»).
- `POST /api/auth/pin` — проверка PIN → сессионная httpOnly-cookie.
- `POST | PUT | DELETE /api/blocks/{id}` — создание/правка/удаление блока (только с сессией; серверная валидация пересечений — та же логика, что в интерфейсе).
- `PUT /api/blocks/{id}/curator` — назначение куратора manual-блоку (только с сессией).
- `GET /api/audit` — журнал правок.

**Хранение:** SQLite через PDO (`pdo_sqlite`), файл БД — **вне webroot** (в домашнем каталоге хостинга), чтобы не был доступен по URL. Резерв: если на тарифе `pdo_sqlite` недоступен (проверяется при деплое) — MySQL из панели хостинга; структура таблиц (раздел 3) совместима с обоими вариантами.

**Планировщик:** Crontab в панели Timeweb → `php notify.php` по будням в 7:00 МСК (раздел 6). На этапе 1 — сухой прогон в лог.

**Деплой:** GitHub Actions при пуше в `main`: сборка фронтенда → выгрузка статики и PHP-файлов на хостинг по SSH (rsync) или FTP (доступы — в секретах репозитория). Ручной запасной путь: `git pull` по SSH прямо на хостинге. Подробности — раздел 9.

## 8. Безопасность и доступ

- Просмотр — публичный, без авторизации (решение заказчика; из персональных данных на сайте — только ФИО ординаторов и заведующих и график ротаций).
- Редактирование и кабинет учебной части — только после ввода **PIN-кода** (один PIN, единая привилегированная сессия; при необходимости позже разделяется на два кода без изменения архитектуры): PIN хранится на сервере в виде хэша (`password_hash`), проверка на сервере, при успехе — сессионная httpOnly-cookie; все изменяющие API-запросы без валидной сессии отклоняются. Ограничение перебора: не более 5 попыток ввода PIN за 15 минут с одного IP.
- Вся валидация (пересечения блоков, диапазоны недель, существование сущностей) дублируется на сервере — фронтенд-проверки считаются только удобством.
- HTTPS — бесплатный сертификат Let's Encrypt из панели Timeweb, HTTP → HTTPS редирект.
- Файл БД — вне webroot; журнал правок (`audit_log`) не отключается.

## 9. Деплой и сопровождение

- **Адрес:** поддомен на существующем домене заказчика, рабочий вариант — `rotation.mmcc-education.ru` (создаётся в панели «Домены и SSL»; финальное имя — на усмотрение заказчика).
- **Первичная настройка** (делается один раз, по README репозитория — Claude Code расписывает каждый шаг вплоть до кнопок панели Timeweb): создание поддомена и выпуск SSL; создание SSH/FTP-доступа; добавление доступов в секреты GitHub-репозитория; первый деплой через GitHub Actions; инициализация БД из `data/seed.json`; установка PIN администратора; настройка Crontab (ежедневная задача 7:00 будни + еженедельная копия файла БД в отдельную папку).
- **Обновления:** правка кода → пуш в `main` → GitHub Actions собирает и выкладывает автоматически. Данные при деплое не затрагиваются (БД живёт отдельно от кода).
- **Резервные копии:** еженедельная cron-копия файла БД + штатные резервные копии панели Timeweb. Восстановление = возврат одного файла.
- **Смена учебного года:** новый набор ординаторов и календарь недель загружаются новым seed-файлом (процедура описывается в README); прошлогодние данные архивируются копией БД.

## 10. Этапы работ и критерии приёмки

**Этап 1 — MVP:** структура БД + импорт seed.json; три экрана по разделу 5; PIN-авторизация и редактирование; журнал правок; деплой на поддомен через GitHub Actions; `notify.php` в режиме сухого прогона.

**Этап 2 — уведомления:** Telegram-бот, привязка кураторов кодами, боевая рассылка по разделу 6.

**Критерии приёмки этапа 1:**
1. График на сайте полностью совпадает с Приложением В (включая исправление Шидаевой).
2. Кабинет куратора корректно делит ротации на «сейчас / завершили / придут» относительно текущей даты; для кандидатов ЦАОП отображаются «возможно ваши».
3. Назначение куратора manual-блоку в админке сразу отражается в кабинете этого куратора и в матрице (⚠️ исчезает).
4. Попытка сохранить пересекающиеся блоки одного ординатора отклоняется с понятным сообщением.
5. Правки переживают перезагрузку страницы и видны с другого компьютера; каждая правка есть в журнале.
6. Без PIN изменить данные невозможно (в т.ч. прямыми запросами к API).
7. Кабинет учебной части закрыт PIN-кодом и корректно показывает по каждому куратору задачи дня: «подписать логбук» (в течение 5 рабочих дней после окончания блока), «принимает» (первая неделя блока), счётчики сводки и список блоков без куратора.
8. Сайт открывается по HTTPS на согласованном поддомене; матрица читаема на экране 1366×768.

**Критерий приёмки этапа 2:** тестовый куратор получает сообщение в 7:00 рабочего дня при наличии событий и не получает ничего при их отсутствии.
